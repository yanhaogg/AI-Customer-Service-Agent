# Agent 实测报告：2026-10-26

本报告记录当前代码的一次真实模型实测，不是生产环境 SLA，也不代表任意问题的回答准确率。评测期间未修改 Agent 提示词或业务代码来提高分数，没有删除失败样本。

## 测试条件

- 模型：项目当前配置的 `deepseek-flash`，使用真实模型服务，不是模拟模型；服务别名未锁定供应商内部模型快照。
- 常规集：12类固定题目各问2次，共24条评分请求，覆盖商品售价/参数、订单状态/物流、退款政策、浏览、聊天搜索、无库存、跨用户订单和复合问题。
- 状态变更补测：同一会话先问商品和订单（2条预热，不计评分），随后将演示售价299改为349、已支付订单改为已发货；各追问2次，共4条评分请求。
- 总计30条真实聊天请求，其中28条计入评分与延迟统计，2条预热排除。常规集与变更补测分别使用新的隔离样本环境。
- 数据为临时 PostgreSQL schema 中的合成商品、订单、浏览和聊天；不读取真实客户资料，结束后删除临时 schema。
- 请求串行执行，无并发压测。计时从 FastAPI TestClient 调用客户消息接口到完整答案返回，包含 JWT校验、消息持久化、Manager/专员、远程模型及数据库工具，不含浏览器传输、公网客户端往返或首字延迟。
- 同一订单按应用规则复用会话，后续提问会带上先前回答，样本不是相互独立的。该设置暴露了重复咨询时使用旧答案的问题。
- 设置与依赖版本、代码文件哈希见 JSON。默认预算不是测试结果，不用它替代响应时间。

跨用户订单查询的两次 `not_found` 是预期的安全拒绝，不是数据库执行异常。工具执行成功率只衡量**已经发起的调用**是否按协议结束，不能说明模型是否选择了正确工具或是否遗漏查询。另列的本轮查询要求通过率用于观察这件事。没有查询的快速回答同样计入总延迟，不能将4.68秒解释为每次完整多工具链路耗时。

## 评分口径与限制

题目和规则在执行前写入脚本。按数据库中已知事实设置正则断言，例如售价299、续航30小时、重量180克、快递单号、质量问题需人工和照片；跨用户问题额外检查不泄露私有承运商和单号。每题全部断言通过且消息正常完成才计为事实通过；工具证据独立评分，再取二者交集。

这是**小型固定集的关键事实断言通过率**，不是对所有句子的语义正确性、完整性或无幻觉率评估。断言之外的附加说明不被完整覆盖。样本少、是合成数据、没有同义改写大样本和模型对比实验，不能直接推广到生产准确率或声称效率提升百分比。

## 发现的问题

1. 常规集6条回答虽然核心事实符合静态数据，但没有重新调用所需工具，部分还声称“已核实”。应计为本轮查询要求不通过，不以文字正确掩盖证据不足。
2. 状态变更后一次订单回答沿用旧上下文：实际订单已发货，模型仍回答未发货，且本轮没有工具调用；下一次追问重新查询后才纠正。原始失败样本见补测 JSON 的 `paid_order`、`repetition=1`。
3. 工具执行36/36正常并未防止上述错误，说明工具的可执行性与调度的查询遵循是两类指标。

当前优先改进方向是确保涉及实时业务事实时实际查询，而不只是继续增加提示词或仅统计工具成功率。此报告没有实施该改进，也不报告未经测量的提升。
